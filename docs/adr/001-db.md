# ADR 001 — Database Client and Migration Strategy

**Date:** 2026-06-06
**Status:** Accepted

## Context

The in-memory `users` and `sessions` Maps need to be replaced with a real database so data survives server restarts. We need to choose a DB, a client/ORM, and a migration tool.

## Decision

**Database:** MongoDB
**Client / ORM:** Prisma
**Migration tool:** Prisma Migrate (via `prisma migrate dev` / `prisma migrate deploy`)

## Rationale

### MongoDB

- Schema-flexible documents suit auth data that may grow extra fields (e.g. OAuth profiles, metadata) without requiring ALTER TABLE migrations.
- No joins needed for this domain — user and session documents are self-contained.
- Prisma supports MongoDB with a first-class provider.

### Prisma

- Single source of truth: `schema.prisma` defines models, generates a type-safe client, and drives migrations.
- The generated client replaces raw query strings — reduces surface area for injection bugs.
- `prisma migrate dev` handles schema evolution during development; `prisma migrate deploy` applies migrations in CI/prod.
- Straightforward to swap the provider later if requirements change.

## Consequences

- `DATABASE_URL` env var required (MongoDB connection string).
- `src/store/users.js` → replaced by Prisma client calls in DB-2.
- `src/store/sessions.js` → replaced by Prisma client calls in DB-3.
- `prisma/schema.prisma` becomes the canonical data model.
- Prisma Client must be generated (`prisma generate`) before the app starts — added to `postinstall` script.
